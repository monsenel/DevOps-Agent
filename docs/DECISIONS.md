### D-026 · 2026-11-15 · Auto execution mode disabled for MVP
- **Decision:** Execution modes are `ReadOnly` and `Confirm` only. "Auto within allowlist" is removed from the Settings UI, from save/validation, and from every execution path (approval, agent dispatcher, Updates page); every mutating call needs explicit approval unless a read-only group blocks it. A stored Auto value (mode `2` in the `agent.execution-modes` setting) reads as `Confirm`, not as corrupt; stored allowlists are ignored. Genuinely unreadable, null or unknown values still fail closed to `ReadOnly`. Supersedes the auto-within-allowlist part of AGT-3 and T6.1.
- **Why:** Owner decision 2026-11-15. Server output is untrusted text and can carry prompt injection; letting a model-chosen tool call run without a human approving the exact command is an unacceptable risk for the MVP.
- **Consequences:** `ExecutionMode` has no Auto member and `ExecutionModePolicy` has no allowlist. Data written earlier keeps working (Auto becomes Confirm). "Auto within allowlist" moves to the v2 backlog and needs its own design (command pinning, per-tool scopes) before returning.


### D-027 · 2026-11-15 · Read-only groups never write on the server
- **Decision:** `ReadOnly` means no writes on the server at all, including refreshing package metadata. Update scans for servers in a read-only group (or when the execution-mode setting is unreadable and fails closed) run `apt list --upgradable` / `dnf -C check-update` / `dnf -C updateinfo list security` without sudo, and never `apt-get update`. The agent's read-only `list_updates` tool is cache-only on every group. Each scan records when the package lists were last refreshed (newest mtime under `/var/lib/apt/lists`, or the dnf solv cache), and the Updates page shows it, labelled "cached lists only" for read-only groups. Non-read-only groups keep refreshing lists with sudo during scans (T6.5).
- **Why:** Owner decision 2026-11-15. `apt-get update` rewrites the package cache; a read-only group must not be modified by the app.
- **Consequences:** Read-only scans can be stale; the last-refreshed time makes that visible. `UpdateScans` gains `CacheOnly` and `PackageListsRefreshedAtUtc` (migration `AddUpdateScanCacheInfo`, additive).

### D-030 · 2026-11-15 · block_ip refuses addresses that would lock out the app or the operator
- **Decision:** `block_ip` is denied when the address is loopback, unspecified, broadcast or multicast; one of the app host's own interface addresses; any inventory host (so every jump host), by literal IP or by name resolved from the app host; or a client address the signed-in operator has used to reach the app (recorded per authenticated request, last 32, in memory). The check runs when the action is proposed and again when it is approved.
- **Why:** Review finding (T7.R4): one mistaken or prompt-injected ban could cut the app off from a jump host and every server behind it, or lock the operator out.
- **Consequences:** Inventory names that only a jump host can resolve are not compared by name; their literal addresses still are. Operator addresses are forgotten on restart until the next request.

### D-031 · 2026-11-15 · Sudo alerts exempt only the app's own fixed command lines
- **Decision:** A sudo event by a server's inventory SSH user is exempt from the "sudo by non-allowlisted user" alert only when its command is the `sudo -n true` probe or exactly one of the command lines in `AppSudoCommands`. The list is generated from the same builders that send the commands, with sentinel values replaced by strictly typed holes (hex IDs, numbers, unit/package names, IP addresses, a quoted path). sudo's split `(command continued)` log lines are joined before matching. Supersedes the probe-only rule from b5ec62c.
- **Why:** Owner decision 2026-11-15: the probe-only rule made the app's routine `ss`, `nginx -T`, `nsenter`, scan and update commands raise the alert on every server, burying real signals.
- **Consequences:** Any other sudo by the app user still alerts. A test captures every sudo command the collectors, scanner and tools send and fails if one is missing from the list. Sudoers can pin only the fixed commands while everything runs through `sh -c` (T7.R14).

### D-032 · 2026-11-15 · Per-host SSH backoff and jump short-circuit
- **Decision:** `HostReachabilityTracker` (singleton `IHostReachability`, in memory) records connection-level failures per host: the host is skipped for 1 minute after a failure, doubling up to 15 minutes, and reset by the first success or by a settings change (`Evict`). Only one retry runs at a time; everyone else gets `HostUnreachableException` ("<server> is unreachable [via jump host X] (since …, next retry …)") at once. A server whose jump host is in backoff is unreachable without any connection attempt. `SshRunOptions.BypassBackoff` ("Test connection" and "Retry now", which is the same capability test) attempts the whole route. SSH.NET sits behind `ISshTransportFactory` so the pool's routing and backoff are tested with fakes. Alert evaluation, metrics and health checks run 8 servers in parallel; health checks of a server in backoff are recorded as not probed instead of waiting.
- **Why:** T7.R1 / owner scope 2026-11-15: one blackholed host or jump host made discovery take minutes and the metric cycle overrun.
- **Consequences:** Backoff state is lost on restart (the first cycle after a restart pays one connect timeout per dead host). A server's real SSH status can lag by up to its current backoff; "Retry now" checks immediately.

### D-033 · 2026-11-15 · Stale carry-forward for unreachable servers
- **Decision:** When a server is unreachable during discovery (`HostUnreachableException`), its nodes, listeners, edges and evidence are copied from the last usable snapshot into the new one and marked with node attributes `Stale: true` and `LastSeenUtc` (kept from the first stale copy, so repeated outages keep the real last-seen time). A server with no history keeps a bare host marked "never discovered". Drift compares node attributes without those two markers, so an outage or a recovery is not drift. The graph dims stale nodes and adds "stale · last seen <time>" to the label; the detail panel and the keyboard node list say the same in text. Docker's embedded DNS listener (127.0.0.11, random port per container start) is one listener identity per protocol for drift.
- **Why:** NFR-3 and T7.R2: an unreachable server's nodes vanished, producing "removed" drift and, on recovery, "added" drift and new-listener alerts.
- **Consequences:** Only unreachable servers are carried forward; a reachable server whose individual collector fails still loses that collector's nodes for the run. Observed connections that other, reachable servers make to a recovering server can still appear as removed until those clients reconnect.

### D-034 · 2026-11-15 · Container restart-loop rule
- **Decision:** Each metric cycle also runs a read-only container query (`docker ps -aq` + `docker inspect` ID, name, state, restart count; a marker when Docker is absent), without sudo, repeated with sudo only when Docker refuses and the server is sudo-capable (the command is on the `AppSudoCommands` list). The last 30 minutes of per-server container lists are kept in app settings. A container in state `restarting`, or whose restart count rose by 3 or more within 10 minutes, raises a medium `container-restart-loop` alert; it resolves 10 minutes after the last restart or when the container disappears. A recreated container (new ID, counter reset) is not counted as a restart. The High `container-state` alert no longer fires for `restarting` (it covers exited/dead containers).
- **Why:** T7.R3 / MON-2: restart loops were only visible as a generic "restarting" state alert.
- **Consequences:** One extra read-only SSH command per server per minute. History starts when the app starts, so restarts before that are not counted.

### D-035 · 2026-11-15 · Restart-loop rule needs two `restarting` samples
- **Decision:** Supersedes the "a container in state `restarting`" trigger of D-034: the state counts as restart activity only when the same container (same ID) was also `restarting` in the previous metric cycle. A restart-count rise of 3 or more within 10 minutes is unchanged. Only activity inside the 10-minute window can open or keep the alert, so one later restart does not reopen a resolved loop.
- **Why:** Review of T7.R3: one sample landing in the short pause after a single crash opened a Medium alert and a notification, although a single restart must not alert.
- **Consequences:** A loop that is only visible as `restarting` alerts one cycle (about a minute) later. Real loops back off exponentially, so they stay in `restarting` and their counter rises well within that time.

### D-036 · 2026-11-15 · Leased SSH clients: retire and drain instead of dispose
- **Decision:** Every command runs on a lease of a pooled client (`ISshConnectionPool.GetSessionAsync` returns an `ISshCommandSession : IDisposable`; `SshRunner` disposes it in every outcome, and disposing is idempotent). `Evict` (host edit, delete), a dead transport, and the third consecutive command timeout (`SshTimeoutTracker`, one per entry) only **retire** the entry: it leaves the pool, takes no new leases (callers connect a fresh entry meanwhile) and its client is disposed when its lease count reaches zero, at once when it is idle. A dependent entry holds a lease (a counted "jump reference", not a command) on its jump entry from creation until its own client is disposed, so a jump tunnel outlives the commands running through it and closes after the dependent. A retired jump entry stays open while a pooled dependent still uses it; the dependent's next request notices the replaced jump entry, builds a new entry and releases the old chain. Pool `Dispose` (shutdown) closes every client at once, leased or not, dependents first, including entries that are still draining. A command is closed under only by shutdown or its caller's own cancellation. `SshConnectionPool.ActiveLeases` / `LiveClients` expose command leases and open clients for tests and diagnostics; the pool logs retire/dispose at Debug (server name and reason only).
- **Why:** T7.R15: `Invalidate`/`Evict`/timeout recycling disposed the client under running commands; measured live (see PROGRESS), a 60 s command lost its client in the same instant as a host edit (20 s into the command) and then hung until its own 120 s timeout instead of finishing. Short probes (30 s metrics, 20 s status) could kill a 10-minute `apt upgrade`.
- **Consequences:** A name-only edit never evicts (`ServerService`, unchanged), so only edits of host, port, user, key, passphrase or jump server retire a client. Disposing a client does not make SSH.NET fail a command that is already running on it (the command hangs until its own timeout); that is why retire-and-drain, not dispose, is required, and it also means commands in flight at shutdown are not woken by `Dispose` (T7.R17). A retired client with a hung command stays open until that command's timeout ends it.

### D-037 · 2026-11-15 · Hung commands back a host off; one deadline per call; shutdown abandons SSH work
- **Decision:** (1) `IHostReachability` counts consecutive command timeouts per host (they survive a recycled client and end with the first command that completes). The fourth in a row (`CommandTimeoutThreshold = 4`, one more than the three that make `SshTimeoutTracker` recycle a client, so the fourth ran on a fresh connection) puts the host in the same backoff as a connect failure (1 minute doubling to 15), with `HostFailureKind.CommandTimeout`. Callers are then skipped at once, also on a still-connected client, and a server behind it is "unreachable via jump host X: commands on X timed out". After the backoff any caller may probe: one more timeout doubles it, the first completed command clears it, a connect alone does not. Timeouts that were already running when the backoff began do not escalate it; "Retry now" (bypass) does extend it when it times out again; a host edit (`Evict`) resets state and count. Messages end in the cause, "could not connect" or "commands timed out". (2) `SshRunOptions.Timeout` is the deadline of the whole call: the pool cuts a connect, or a wait behind another caller's connect, off when it passes (the host counts as having failed to connect), and the first command gets what is left. The pool also enforces command timeouts itself (abandoning the wait) because SSH.NET cancellation and timeouts do not always end a command on a dead peer. (3) The auth-log scan is skipped when the status probe failed; the saved scan state (`IAuthLogScanSource.GetCachedAsync`) is reported instead, so recent security alerts stay. A failed probe reads "status probe failed: <reason>". (4) `MonitoringCycleOptions`: the remote part of a metric cycle has a deadline of 50 s and of an alert evaluation 25 s (intervals 60 s / 30 s); a host still being polled when it passes is marked failed for that cycle, the other hosts' results are stored. The container query of a metric cycle has its own 10 s budget for both attempts and never costs the metric sample. (5) Shutdown: `SshConnectionPool` takes `IHostApplicationLifetime`. Once `ApplicationStopping` is set no connection or command starts (`SshShutdownException`, an `OperationCanceledException` subtype), connects and commands in flight are abandoned at once whatever token their caller passed, a connection finished late is closed, and the pool never throws `ObjectDisposedException` (connect gates are no longer disposed). The stopping signal reaches the pool and the hosted services through `DetachedCancellation`, so the continuations of abandoned waits run on a pool thread, not on the SIGTERM thread, and an abandoned `SshClient` is disposed in the background. Hosted services link to ApplicationStopping (their own token only fires when the host reaches them in its sequential stop). New Blazor circuit connections (`/_blazor`) get 503 once the host is stopping. `docker-compose.yml` gets `stop_grace_period: 40s`.
- **Why:** T7.R17. Measured on the lab (PROGRESS): SIGTERM with a blackhole connect in flight took 28.8-30.1 s and another connect started after "Hosting stopping" (a service whose token had not been cancelled yet, and an `SshClient.Dispose` that blocked for the connect timeout inline on the SIGTERM thread); a paused host held every alert evaluation for 30 s (status probe plus auth scan).
- **Consequences:** A command abandoned by a deadline or by shutdown can keep running on the remote host until its own channel closes (as before for timeouts). A host whose Docker daemon hangs but whose SSH works is backed off only if four commands in a row time out, which the interleaved successful metric command prevents in the monitoring cycles; discovery (collectors run back to back) can trip it. A cycle cut by its deadline does not count as a command timeout (the per-call deadlines are shorter). `docker pause` of a lab server makes new connections hang in the SSH handshake, so it first shows as three command timeouts (recycle) and then as a connect backoff; the command-timeout backoff needs a host that connects but does not answer (live harness, see PROGRESS). Metric samples are stamped when the whole cycle has finished, so a cycle that waited 15 s for a dead host shifts every host's sample time by that much (not changed here).

### D-038 · 2026-11-15 · Container states, stale data and Docker failures in the restart-loop rules
- **Decision (container states, owner 2026-11-15):** `exited`, `dead` and any unknown state keep the High `container-state` alert from the status probe (one alert per container, key `container-state:<server>:<name>`, unchanged). `restarting` stays with the restart-loop rule. `paused` raises a Low `container-state` alert as soon as the stored sample shows it. `created` and `removing` raise nothing until the same container (same ID) has been in that state for more than 10 minutes, measured from the first stored sample of the run in the per-server container history (not from the wall clock); then a Medium alert; the alert ends with the state. The new alerts use the key `container-state:<server>:<name>:<state>` and come from the container history, not from the live probe, so they follow the same stale-data rules as the restart loop. They appear up to one metric cycle (about a minute) after the state starts. Supersedes the behaviour in which `created`, `paused` and `removing` raised the High `container-state` alert (T7.R18 (e)).
- **Decision (blind spots, documented):** the restart-loop rule reads Docker's `RestartCount`, which only counts restarts by the restart policy. A recreate loop (the container is deleted and created again, for example by a compose or orchestrator loop: new ID, counter back at 0, D-034) and a manual `docker restart` (does not change `RestartCount`) are invisible to it; so is one restart. Only a counter that rises by 3 within 10 minutes, or two consecutive `restarting` samples (D-035), opens an alert.
- **Decision (stale data, T7.R18 (a)):** when the latest stored sample of a server is older than 3 minutes (unreachable, in backoff, probe or container query failing, app was stopped) the container rules are evaluated as of that last sample: nothing resolves, ages, or opens from the missing data. After a gap longer than 3 minutes a loop that was open before it stays open until 10 quiet minutes have been seen in fresh samples after it. Sampled time, not wall-clock time, ages the stored history (30 minutes of sampled time are kept; gaps do not count). Stored history is dropped when older than 24 hours, whenever it is read or written, so a server that stays unreachable for more than a day also loses its held alerts. `exited`/`dead` are unchanged: they come from the live probe and resolve while the server is unreachable (the unreachable alert covers it).
- **Decision (partial inspect, (b)):** `docker inspect` exiting 1 because one container disappeared between `ps` and `inspect` is not a failure: the others are parsed, the command exits 0 and no sudo retry follows. The exit code survives only when `inspect` printed no container and did not report a missing object.
- **Decision (Docker permission, (c)):** the alert status probe reports a Docker permission failure with its own marker instead of swallowing it (the `|| true` stays on `systemctl` only, so a host without systemd is not a failed probe). On "permission denied" and a sudo-capable server the same read-only command is repeated with non-interactive sudo (`AlertSignalSource.StatusCommand` is on the `AppSudoCommands` list, D-031). If Docker is still refused, a Medium `docker-status-unavailable` alert with fixed text (no server output) reports that container alerts are not working; the server itself is not marked unreachable and its other checks and the auth-log scan continue. A host without Docker, or with a stopped daemon, stays silent as before.

### D-039 · 2026-11-15 · Login failures are their own state; connects are single-flight; shutdown never throws
- **Decision (classification):** `HostFailureKind` gains `AuthFailed`. (3) Any success of a connection clears the count. (4) A failure of another kind in between (connect failure, or a command-timeout backoff) breaks the run of *consecutive* auth failures: the next login failure starts again at 1 (the existing change-of-kind rule). Counts are per host. The state is in memory only (the tracker): an application restart forgets it and allows three more attempts. While a host is paused the existing auth-failed alert stays open (the condition keeps being reported, nothing resolves it) and its details say that automatic retries are paused; metric, health-check and discovery consumers treat paused like auth-failed backoff (skipped, stale carry-forward unchanged). Supersedes "retried every minute and never less often" above and the "attempted once a minute forever" consequence below.
- **Amendment (review-r2, 2026-11-15):** a server that closes the connection while the key is being offered (sshd `MaxAuthTries`, a login penalty: SSH.NET raises `SshConnectionException`, not `SshAuthenticationException`) is a failed login too: `SshNetTransportFactory` remembers that the key method ran (`KeyAuthentication`) and reports a hang-up after that point as `SshAuthFailure.ServerClosedDuringLogin` ("the server closed the connection during login"). A drop before the key is offered, or after the connection is up, stays a connection failure. A server behind a jump host whose login failed gets its own `ssh-auth-failed` alert (title "... on jump host <edge>"); if the jump host is only down it gets `server-unreachable`, as before. A host-key mismatch somewhere on the route stays `server-unreachable` for the dependents (not a login failure). Notifications are unchanged (D-028): "[High] <server> · ssh-auth-failed · opened|resolved", no key path, user, address or text. The only strings that mention the rule are the signal source, the tests, the alert-rule list in `PLAN.md` T5.3, `ARCHITECTURE.md` and this file; there is no rule catalog, settings screen or counter that filters on `server-unreachable` (checked: every use of the string in `src/`, `tests/`, `docs/`). Migration: an alert for an auth failure that is still open from an earlier build is resolved by the first evaluation after the upgrade (its key is gone) and a new `ssh-auth-failed` alert opens, with one resolved and one opened notification.
- **Decision (single-flight):** the connect attempt is a `ConnectFlight` owned by the pool, not by the caller that started it: its own cancellation (host stopping, edit of the server, pool closed, every caller gone), one outcome handed to every caller at once. Callers that arrive while it runs share it when the host has no failure on record (first connect, or after an edit) or when both are "Retry now"/"Test connection" attempts; a retry of a host in backoff stays its claimant's alone and everyone else is told at once (D-032), and "Retry now" arriving behind a retry that is not its own waits for it and then makes its own attempt. A caller whose deadline passes or that is cancelled only stops waiting; the last caller to leave ends the attempt (a deadline counts as a failed connect, D-037, and that caller reads the failure it caused; a cancellation records nothing). An edit ends an attempt in flight and its callers start over with the new settings. This replaces the per-server connect semaphore. Measured on the previous code (HEAD 131e5a0): ten concurrent first calls already made one attempt (the later ones queued at the semaphore and then found the backoff), but ten concurrent "Retry now" calls made ten attempts one after the other (6.1 s with a 0.6 s connect) and the first caller's own short deadline ended the attempt, backed the host off and failed every other caller.
- **Decision (shutdown):** `Dispose` is idempotent and thread-safe (atomic flag), ends connect attempts in flight on a pool thread, closes every client and never disposes anything a caller can still reach; `SshNetTransport.Dispose` is idempotent and never throws; a late connection is closed by the continuation that notices the abandoned attempt (which also never throws). The shutdown race tests found a real lock-order inversion (cancelling a connect ran its continuations inline under the flight's lock while the pool takes the two locks in the other order): nothing is called out to under a lock now (`Cancel` and `Dispose` of the cancellation source happen outside it).
- **Why:** T7.R19, owner scope: a wrong or missing key was reported as an unreachable host, hidden for up to 15 minutes, and Test connection said only "unreachable since …".
- **Consequences:** Not done (not in the owner's list; moved to the v2 backlog in PLAN.md on the owner's order): claim token so a cancelled caller cannot clear a bypass caller's in-flight flag, checking the target's own backoff before connecting its jump host, the Servers page "Not tested" versus "Reachable" label. A server whose key is rejected was first attempted once a minute forever (a handshake and a failed login per minute), which on a server with fail2ban could ban the app's own address; the amendment above stops the automatic attempts after three.

### D-043 · 2026-11-16 · edit_config: staged, hashed, backed up, validated, reloaded, health-checked, rolled back (T8.8)
- **Decision:** a mutating tool `edit_config` (one server, always approval, refused on read-only groups like every mutating tool, D-027). Allowed paths: `ConfigEdit:AllowedPaths` (default `/etc/nginx/**`; `**` any depth, `*` within a name), plain absolute paths of safe characters only, the sensitive-path deny list on top. The model gives the full new content or a unified diff; before the proposal is stored the app reads the file (read-only, as the SSH user, sudo only when it cannot read it) and stores the full new content, the current file's SHA-256 and a diff, which the chat card and the Action log show for review (a proposal that arrives already "prepared" is refused). Execution: (1) the SSH user stages the content in a private `mkdir -m 700 /tmp/dva-edit-<action id>` (the content never appears in a sudo command line or in auth.log) and its hash is checked; (2) one root step refuses a file that changed since the proposal (hash), copies it to `path.bak-<unix time of the proposal>`, writes a temporary file beside it, copies mode and owner, `mv`s it into place, runs the validation command (`ConfigEdit:Services`, default nginx: `nginx -t`) and the reload (`systemctl reload nginx` when systemd runs it, else `nginx -s reload`), restoring the backup (and reloading) if either fails; (3) health check: the server's enabled health checks, and each domain whose server block is in the edited file (all nginx domains for another nginx file) requested through the server's own listener (`curl -H 'Host: <domain>' http://127.0.0.1:<port>/`, no answer or 5xx = failure); (4) on a failed check a root rollback restores the backup, validates and reloads; (5) the staging directory is removed in every outcome. The result names the failed step. The apply, rollback and sudo-read commands with the default nginx rule are in `AppSudoCommands` (custom validate/reload commands are not exempt from the sudo alert).
- **Review-r4 (2026-11-16):** a path that is or lies behind a symbolic link is refused on the read and in the root step (`readlink -f` must equal the path; the allowlist and the deny list judge text and a link could lead anywhere, and `mv` would replace the link with a file); a restore is reported only when its copy worked (`DVA_RESTORE_FAILED` otherwise, nothing is reloaded from it); a health check that cannot be completed counts as failed and rolls back, and the rollback is not cancellable; the sudo-alert exemption of the apply, read and rollback commands covers only `/etc/nginx/…` paths (no `..` segment) and the action's own staging file. Open: T7.R28.
- **Consequences:** backups stay beside the file (as the owner asked); with an `include …/*` wildcard that matches them (e.g. `sites-enabled/*`) nginx would load them, `nginx -t` would then fail and the edit roll back, so edit files under such directories by changing the include or the allowlist. The chat tool list offers `edit_config` when the prompt mentions changing a config. Live (2026-11-16, srv-edge, isolated DB, staging in Confirm, a stand-in model producing the tool calls): upstream `srv-app:5000` → `5999`: `nginx -t` ok, reloaded, `api.test.local` answered 502 (app.test.local 200) → backup restored, `nginx -t` ok, reloaded, md5 of `demo.conf` identical to before, api 200 again, staging directory gone; `keepalive 8` → `16`: succeeded (both domains 200) and was changed back the same way; no `ssh-unusual-sudo` alert for the app's own edit commands; test backups removed from the lab afterwards.

### D-045 · 2026-11-16 · Agent tool-call limit, final summary, Continue and loop guard (T8.10)
- **Before:** `MaxToolRounds = 5` model rounds of at most 8 calls each; reaching it ended the turn with a fixed sentence.
- **Decision (limit):** a budget of **tool calls per message** (every dispatched call counts, a proposal for approval included), set in Settings › LLM connection (`Chat.ToolCallLimit`, default 15, 1–50). The conversation's effort can only lower it: Low 8, Medium 15, High 30, never above the setting (`ToolCallLimitService.Effective`). Calls of a round that no longer fit are not run (a native tool-call message still gets a "not run" result for each).
- **Decision (summary):** reaching the limit makes **one last model call without tools** (no tool definitions, and the system message without the JSON tool protocol): the results so far travel as one text message, with the instruction to say what was found, what is still unknown and what would be done next. The turn stores "Tool limit reached (N/N)" (role `tool_limit`) and then the summary as the assistant message. A model that answers in text before the limit is not summarised.
- **Decision (Continue):** the button under that summary calls `ChatService.ContinueAsync`, which stores a Continue request as the owner's message and runs a normal turn with a fresh budget. The tools and context are chosen from the original task's wording, not from "Continue"; the agent's own summary, stored in the conversation, is what carries the findings (only user and assistant messages are replayed to the model). It is refused unless the turn after the last owner message stopped at its limit.
- **Decision (loop guard):** the same tool with identical arguments (compared canonically, property order and spacing ignored) **requested** `LoopRepeats` = 3 times in one turn stops the turn: the third request is not run. The turn gets the same tool-free summary call, with the loop named in it, and the banner "Stopped early: <tool> was requested 3 times with identical arguments" (role `tool_loop`). It is not a limit: no Continue button, no N/N.
- **Decision (list):** the calls of a turn (`tool_run`) are drawn as one collapsible list under the line "Ran N tools on M servers" (role `tool_turn`, stored once per turn; "on M servers" is left out when no server was involved). Older conversations, whose per-round "Ran N read-only tools …" lines have no `tool_turn`, are drawn as before.
- **Consequences:** the system prompt still says "Use at most two relevant read-only calls per question"; models follow it, so the limit mostly matters for runaway loops and long investigations. Relaxing that sentence is a separate decision. Live (2026-11-16, isolated DB, a scripted OpenRouter stand-in, both themes): limit 3 → three calls, "Ran 3 tools", the banner, the summary and Continue; Continue → one call and the answer, the button gone; the same call repeated → two runs, the red banner, a summary, no Continue; Settings refused 0 and 51 and saved 3.

### D-049 · 2026-11-16 · nginx `set` variables resolve proxy targets (T8.14, owner bug)
- **Context:** the owner's reverse proxy uses `set $map_app_upstream http://192.168.20.14:3030;` then `proxy_pass $map_app_upstream;`. Every target with `$` was unresolved, so the proxy was not linked to the backend server in the inventory.
- **Decision:** the nginx parser resolves a proxy target of the form `[scheme://]$name` or `${name}` (optionally followed by a literal `/path`) from the nearest enclosing `set` (location, then outer locations, server, http/stream). It stays unresolved, as before, when that scope sets the variable to different values, the value is empty or contains `$`, the only `set` is inside an `if` block, or the variable is an nginx built-in. The resolved proxy keeps the original directive (`ResolvedFrom`: variable, value, file, line; optional in stored JSON) and the edge evidence reads `proxy_pass $var; via set $var value; (file:line)`. The value then goes through the existing name resolution and edge resolver.
- **Also fixed:** proxies inside nested locations were dropped by the parser, and `${name}` broke the tokenizer.
- **Consequences:** a `set` overridden inside an `if` resolves to the unconditional value, which nginx may not use at runtime. Checked on the owner's stored configuration: `$tiles_upstream` → `192.168.20.14:8080` (3 proxies) and `$map_app_upstream` → `192.168.20.14:3030`, which resolve to the `kartio-tiles` and `kartio-map-app-1` containers of the `map` server after the next discovery.

### D-050 · 2026-11-16 · BusyBox hosts: text fallbacks for addresses, routes, listeners and connections (T8.15, owner bug)
- **Context:** on the owner's Alpine 3.23 reverse proxy (BusyBox 1.37) the host collector failed (`ip -j` is not supported) and listeners/connections were skipped (no `ss`), so the server had no addresses and its nginx never became a row on the map.
- **Decision:** all read-only, each step only when the previous one fails or is missing:
  - host: `ip -j addr` → `ip -o addr show`; `ip -j route` → `ip route show` (each falls back on its own; the parser accepts JSON or text; MAC/state/MTU may be null);
  - listeners: `ss -tulpnH` → `netstat -tulpn` (sudo like `ss`, in the sudo allowlist) → `netstat -tuln` without sudo (BusyBox built without `-p`; no process names then);
  - connections: `ss -tnH state established` → `netstat -tn` (ESTABLISHED rows only), and `nsenter … netstat -tn` for containers (in the sudo allowlist).
  Listeners and connections are skipped only when neither `ss` nor `netstat` exists.
- **Consequences:** without working sudo (Alpine often has `doas`), `netstat -p` shows no other users' processes, so nginx still has no row of its own (its ports then belong to the host card). IPv6 routes are not read (unchanged). Checked against real BusyBox 1.37.0 output captured locally (`ip -o addr show`, `ip route show`, `netstat -tuln`, `netstat -tn`); the fixtures follow that layout with documentation addresses. Lab (Debian, iproute2 + ss) discovery unchanged: 3 servers succeeded, same cards, rows and edges.
